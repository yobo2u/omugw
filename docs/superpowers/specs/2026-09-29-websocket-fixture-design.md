## 1. 目标与证据边界

让五条 WS 路径能在不需要凭据的 CI 中反复验证：客户端发出的消息经网关到达
正确上游，收到的上游消息经网关符合客户端契约。证明范围必须落到
`入站协议 × 出站 Provider × 端点 × 能力 × 契约版本`，不能用一次握手替代整条
路径的能力举证，也不能把模型列表出现某个 ID 当作有调用权限。

真实录制提供上游行为证据；脚本化反例验证故障处理。二者均可进入测试，但来源
分开记录：手写 mock 不能独自证明上游确实支持某能力，真实录制也不能穷举畸形帧。
合成 chirp 只证明 DSP/重采样正确性；ASR、VAD、可懂音频与打断分别需要对应样本
与事件证据，不以扫频测试冒充。

## 2. 方案取舍

1. **只真实录制上游契约段，四个观测点离线回放，显式因果边（采纳）**：真实上游
   只负责证明「这份上游请求被接受、它这样回复」；网关的两侧行为用独立声明的
   预期来断言。容许两个方向合法交错。
2. **经网关录制全部四段（否决）**：网关发给上游与发给客户端的消息都从网关自己
   身上录下来，回放时再拿来断言网关——网关发了什么，什么就成了正确答案。对
   异构路径，这恰好是需要被检验的那部分。它还要求 WS 生产接线先存在才能开录。
3. **单一全局序列（否决）**：把一次录制时的 goroutine 调度冻结为协议规则，会
   产生偶发失败，也可能强制等待一条本应并发发送的消息而死锁。
4. **仅录上游回复（否决）**：请求错模型、错采样率仍可能回放成功，不满足异构
   路径对上游请求也有断言的既有约定。

## 3. 证据来源：谁录、谁写、谁审

这是方案的核心约束。四个观测点各有唯一来源，加载器按来源标签校验，不能混用：

| 观测点 | 来源 | 为什么 |
|---|---|---|
| 客户端 → 网关 | **人工编写**（入站协议） | 被测输入，本来就由测试作者决定 |
| 网关 → 上游 | **人工编写的上游请求，录制时由录制客户端直连上游原样发出**（`upstream-accepted`） | 真实上游接受并正常回复，就是这份预期符合上游契约的证据；**绝不从网关的输出里取** |
| 上游 → 网关 | **真实录制**，去敏后入库（`recorded`） | 上游行为证据 |
| 网关 → 客户端 | **golden**，人工审阅 diff | 与 HTTP golden 同一纪律 |

与现有 HTTP 机制对应：客户端请求由人编写，`UpstreamExpectation` 是独立声明的
上游预期，真实录制只负责上游回复，网关输出走 golden。WS 只是把「一次往返」换成
「一段带因果的消息轨迹」，证据分工不变。

录制段的形状与会话契约 §11 的轨迹一致：录制客户端发往上游的完整消息、上游
回来的完整消息、会话结局，三者就是一次录制的全部内容。

- **同契约路径**：客户端输入与上游预期除 §5 声明的改写名单外逐项相同。
- **异构路径**：客户端输入按入站协议独立编写；它与上游预期之间的对应关系，就是
  被测的转换主张，按会话契约 §4 审阅。
- **异构路径的音频**：上游侧样本由同一合成源经**参考重采样器**离线生成，与网关
  实现无关；回放时对网关输出做格式字段精确比较、长度与频谱按容差比较，容差由
  [#8](https://github.com/yobo2u/omugw/issues/8) 定。只有同契约路径要求音频逐字节相等。

回放时上游始终回复录制内容，因此 §5 对「网关 → 上游」的断言必须严格：它是整条
证据链里唯一保证「录制回复对应的真的是这份请求」的环节。

## 4. fixture 外形与门禁对接

**握手。** 保留 `Fixture.Request` 表达下游握手：`method` 为 GET，`path` 是**不含
query 的门路径**，query 另存于去敏的握手元数据。`checkRouteFixtures` 按
`request.path` 与已开门精确对账，path 带上 query 就永远对不上。
`Response.Status` 表达下游握手结果。新增 `ws` 会话轨迹字段，与 `body`、`sse`
互斥。请求体为空是 WS 握手的合法形态，不能放宽 HTTP fixture 的 `upstream.body`
必填约束来迁就它；WS 的上游握手预期独立校验。

**端点常量。** 为三扇 WS 门新增 `Endpoint` 常量，并纳入 `Endpoint.Protocol()`
的归属判定：

| 门 | 归属入站协议 |
|---|---|
| `/v1/realtime` | `openai.realtime` |
| `/api-ws/v1/realtime` | `dashscope.realtime` |
| `/api-ws/v1/inference` | `dashscope.inference` |

`Protocol()` 对未知门放行，所以不加常量也能 `Redeem`，但那样就失去了 Build 期
「这扇门归谁把守」的错绑检查。门路径以实施时 Mux 实际注册的为准，但必须是常量。

**有损格子沿用文件名约定。** `checkRouteFixtures` 要求每个 DEGRADE/EMULATE 格子
有同名文件，WS 路径照此执行，不改门禁：

| 路径 | 必须存在的同名 fixture |
|---|---|
| `openai.realtime → dashscope.ws.realtime` | `audio_input.json`、`parallel_tool_calls.json` |
| `dashscope.realtime → openai.realtime` | `audio_input.json`、`parallel_tool_calls.json` |
| 两条同源路径、`dashscope.inference → dashscope.ws.inference` | 无有损格子，至少一份覆盖门的 fixture |

fixture 内的「显式能力覆盖」声明是**附加核查**，不替代文件名约定：一份录制可以
同时覆盖多项能力，但同名文件必须存在，且确实触发了它所代表的那一格。

**轨迹元数据**必须含：schema 版本、名称、场景说明；两端协议与契约版本、端点、
模型、采样参数及录制日期；各观测点的来源标签与真实录制的去敏摘要、样本摘要；
上游握手预期（路径、非敏感查询参数、协议头、测试凭据占位）；能力覆盖与关联
断言；握手结局、会话结局及关联 response/task 的终止证据。

## 5. 观测点断言

| 观测点 | 回放时由谁执行 | 必须验证什么 |
|---|---|---|
| 客户端 → 网关 | 测试客户端发送 | 入站原始命令及其明确依赖 |
| 网关 → 上游 | 回放上游接收并断言 | model、命令、格式、字段转换后的完整消息 |
| 上游 → 网关 | 回放上游发送 | 去敏后的真实上游消息 |
| 网关 → 客户端 | 测试客户端接收并断言 | 入站协议信封、关联 ID、错误、用量与内容 |

**同契约路径**：消息负载逐字节保全，**但扣除显式改写名单**。名单按字段路径登记，
每项写明允许的变换；名单外任何差异都失败。目前能预见的一项是模型名：OpenAI 的
`session.update` 可以携带 `model`（研究快照第 537 行），DashScope 的
`session.model` 与握手 query 的优先级未文档化（会话契约 §7）。网关是把逻辑模型名
改写成上游模型名，还是拒绝这个字段，由实施计划按会话契约决定；两种做法都必须在
名单里声明，不能靠通配放过。握手不是应用消息，其凭据清洗见 §7。

**跨协议路径**：两端分别断言，不默认相等。一条上游消息被转换成多条下游消息时，
逐条标明关联，不能用「事件数一样」替代语义验证。

应用层记录**完整 WS 消息**，保留 text/binary opcode 与完整负载；binary 全量编码，
不能只存哈希导致无法回放。网络帧掩码、FIN 分片及 ping/pong 由两个连接端点分别
处理，不要求握手后的 TCP 字节相同。分片、异常控制帧、心跳死锁在 `transport/ws`
本地 TCP 测试中验证，不借真实云会话的偶然分片举证。

## 6. 顺序、因果与交错

每个观测点内部严格 FIFO。消息可带 `after` 引用，表示它依赖另一观测点的某个节点，
例如上游 `session.updated` 依赖收到对应的 `session.update`。不相关的双向消息
允许交错，不把录制时的观察顺序自动转成所有节点之间的依赖；`after` 只表示协议
或被测转换的必要依赖，不由跨 goroutine 时间戳推导。

**交错怎么产生。** 回放方只能控制自己发什么、何时发：测试客户端在观测点 1 发，
回放上游在观测点 3 发。每一步都能算出「依赖已满足、可以发」的就绪集合；集合里
不止一条时，由调度 seed 决定先发哪条。观测点 2 与 4 是被动核验，消息到达即按
FIFO 消费。

**这证明了什么、没证明什么。** 证明的是「网关在这些**到达顺序**下行为正确」；
不证明网关内部 goroutine 调度被穷举——那归 `-race` 与 `transport/ws` 的本地
测试。只要就绪集合曾经多于一条，就至少跑两种不同 seed，核对按节点归一的消息
与结局仍满足同一语义断言。相同 seed 只保证**相同反馈历史/就绪集合下的纯选择
策略一致**；实际读与 write-result 反馈可能竞争，完整 `SendOrder` 与网络到达序列
不保证相同，不为凑确定性停止合法 reader 竞争。依赖严格串行的 fixture 只有一种
合法顺序，加载器区分 serial/multiple，不假装精确计数全部拓扑序或强凑第二种。

加载时拒绝未知观测点、重复节点 ID、缺失引用、依赖环、不可能的方向顺序及超限
轨迹。回放时只消费下一条合法消息，不跳到后面的「相似事件」。没有预期的消息、
未满足因果条件的消息、缺失消息均失败；错误输出只含节点与字段路径，不打印未
脱敏音频或凭据。

计时不进入 golden；回放有独立的有限 watchdog，触发即失败，不是成功收尾。
正常 close 只说明传输结束：预期事件须全部消费，要求完成的 response/task 须有
终态，否则「半截流 + 正常 close」仍算失败。中断用例显式预期缺失终态、不可知
用量及错误/close 结局。不得为让测试变绿而删掉 cancel、音频、工具事件之间的
实际依赖。

## 7. 动态字段、模型位置与脱敏

**动态 ID** 通过带命名空间的绑定归一化：首次出现记录符号，后续引用必须一致。
「首次出现」不区分由哪一方生成——上游生成的 session/response/item/call ID，与
客户端生成的 inference `task_id`、OpenAI `event_id`，走同一套规则。不同实体
不能错误合并，同一实体也不能被换成新符号来掩盖关联错误。只有 fixture 明列的
字段路径允许替换，不能递归删除所有 `id`、`timestamp` 或 `usage`。

**inference 的任务边界。** 一条连接可以顺序跑多个任务，`task_id` 是连接内的
任务分界；`task-finished` 后可复用连接，`task-failed` 后连接关闭、不可复用
（研究快照 §3.2、§6.2）。一份 fixture 可以包含多个任务，绑定按任务区分；
`task-started` 之前发送音频是非法时序。

**模型在哪里。** realtime 两族的模型在握手 query；inference 的模型在 run-task 的
`payload.model`，不在路径也不在 query（研究快照第 48-49 行）。「错模型」断言按
协议族落在对应位置，不能对 inference 检查握手 query。

**脱敏。** 握手沿用敏感头清洗，另补 query 中的 token、key、userinfo，以及携带
凭据的 `Sec-WebSocket-Protocol` token（OpenAI 浏览器鉴权把 key 放在
`openai-insecure-api-key.<KEY>` 子协议里），保留合法的协议协商 token。只检查
`Authorization` 不够。消息内凭据、账号/租户识别信息和素材隐私在落盘前同样校验。
下游与上游各用不同的合成鉴权哨兵离线断言，证明客户端凭据没有被直接转给上游。

## 8. 录制与回放工作流

**阶段 A：上游契约段（不依赖网关 WS 接线，现在即可开始）**

1. 明确录制计划：上游、模型、契约版本、场景、能力、样本与允许开销。
2. 先做不携带业务音频的真实握手/版本探针；模型目录只作候选来源。
3. 通过双重显式 opt-in 进入专用录制入口：`OMUGW_SMOKE=1` 加独立录制 flag，
   入口精确选择测试名。目前没有这个 WS 录制命令，不发布假装可执行的示例，
   也不裸跑 `make smoke`。
4. 录制客户端 → WS 录制代理 → 真实上游。录制客户端发送人工编写的上游请求，
   代理捕获两个方向的完整消息与会话结局。录制本身有总时长、消息数和字节预算，
   这不是生产 WS 会话的 total 超时。
5. 去敏、动态字段绑定、因果边审阅、校验后输出候选文件；不覆盖既有文件。

**阶段 B：网关端到端（`StreamProvider` 与 WS handler 接线之后）**

6. 为每份上游契约段编写入站客户端输入（观测点 1）。
7. 切换到离线回放上游，按 §6 跑多种 seed；审阅观测点 4 的 golden。
8. 证据齐全后同时更新 `Redeem`、两份白名单与生成的矩阵文档。

录制格式须承载 run-task 的二进制音频，但不因此与 realtime 共享语义 IR；
run-task 的 `task-started`、`finish-task`、`task-finished` 时序约束各自登记。

## 9. 体积预算

基准量级沿用决策地图已定的合成样本：约 0.3 秒扫频，base64 后约 20 KB。用于
ASR/VAD 的真实语音样本会更大，必须在录制计划里写明为什么需要这个长度。单份
fixture 与单个路径目录的字节上限在实施计划中定为具体数字，由加载器强制，超限
拒绝入库。

## 10. 录制清单的口径

「约 20 份会话」只是先前估算，不是完成门槛。最终数量按端点、模型契约和能力覆盖
的缺口确定；同一录制可覆盖多项能力，但不同路径仍需各自端到端回放，且须满足
§4 的同名文件约定。

| 上游端点族 | 应有的真实证据 |
|---|---|
| OpenAI `/v1/realtime` | 会话配置、文本、工具、语音输入/输出、VAD、cancel/truncate、分轮 usage |
| DashScope `/api-ws/v1/realtime` | 对应建模能力、图像/commit 模式适用模型、实际格式回显 |
| DashScope `/api-ws/v1/inference` | ASR 与 TTS 的 run/continue/finish 完整任务及二进制消息 |

**24 kHz 与 legacy 16 kHz 两个分支按模型举证。** 新式
`audio.input.format.sample_rate` 只被部分模型接受（`rules_phase1.go` 注释记录的实测是
qwen3.5-omni 系列），
中间代模型会回显 legacy 结构。所以「两个分支各举证」指的是路径实际使用的模型
各自走到哪个分支，就录哪个分支，而不是每个模型都录两份。

同源路径与异构路径可以引用同一份上游契约段，但不能复用对方的投放结论：异构
路径须按自身的客户端输入重放，核验发往上游的转换结果与返回客户端的语义。上游
若有延迟或语音内容的随机性，固定回放使用已录的完整消息；再次真实录制产生新
版本，而不是把随机输出改成通配符让断言自动通过。上游不支持的分支应得到矩阵
拒绝/降级证据，不能为追平分数写成 PASS。当前尚未对这些场景做新的真实录制。

## 11. 断言的语义来源

fixture 机制只负责「按什么证据、怎样核对」，要核对的语义全部来自会话契约。
契约条款变了，对应断言随之改，不在本文件里另立语义：

| fixture 断言 | 语义来源 |
|---|---|
| 同契约负载保全、未知字段哨兵、改写名单 | 会话契约 §3 |
| missing / null / value 三分 | §4 第 1 条，验收场景 1 |
| 动态 ID 显式绑定 | §4 第 2 条 |
| 配置 pending/confirmed、采样率回显核对 | §4 第 3 条，验收场景 2 |
| 缓冲与队列超限可见 | §4 第 4 条 |
| 上游失败不发 101、部分 101 不重试 | §5 |
| cancel 与 truncate 分开、不编造 truncate ack | §6，验收场景 3 |
| 用量按来源记账、去重、当前笔不可知 | §8，验收场景 4 |
| chirp 只证明重采样 | §10 |
