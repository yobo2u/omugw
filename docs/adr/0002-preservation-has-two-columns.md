# 保留度分「设计目标」与「当前可用」两列

保留度这个数字有两个消费者，而它们要的不是同一个东西：文档读者想知道这个网关
最终能做到什么，选路逻辑必须知道此刻真的能走通哪条路。单列必然骗其中一方——
用设计目标选路会挑中尚未实现的路径，用当前可用做文档则看不出系统的最终形态。
因此保留度输出两列：**设计目标**（假定全部实现、全部配置开启）与**当前可用**
（受实现状态与默认配置双重影响）。`BestOutbound` 一律用当前可用列；CI 两列都
对账——设计目标列验偏好序的设计是否自洽，当前可用列验运行时选路是否正确。

当前可用列**受默认配置影响**，并把前提写进数字本身，例如
`0.929（开启 convstore 后 1.000）`。默认配置就是绝大多数人的实际部署，
按它计分才诚实；括号里的补充让另一种部署也能查到自己的数。

## Consequences

同一条路径在两列下取值不同，看文档时必须先看清列名。这个认知负担是刻意付出的
——它换来的是「文档上的数字」与「运行时的行为」不再互相打架，而后者正是这条
决策的起因：一次排查发现零损失的字节直通路径评分只有 0.704，因为分母里混进了
客户端根本表达不出来的能力。
